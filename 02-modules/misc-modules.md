# 外围模块速览

> 这一页把前面没有单独成篇的"小模块"打包过一遍:培训考试、达人探店、合同与年度运营费、门店投诉、门店 AI 摄像头,以及后来补上的抖音团购、物流商仓配、区域代理预存与划店、电子签导入,共九个;另附礼品商城的一条指引(它的机制正篇在积分体系那页)。每个模块只讲两件事——它解决什么问题、有哪个设计点最值得抄。适合快速扫读,也适合作为"我们还缺什么"的对照清单。

**读完你会知道:**

- 这九个外围模块各自解决什么问题,以及每个模块最值得抄走的一个设计点
- 为什么"培训完成度进经营分"比"发通知催学习"有效得多
- 费用折算这种口径敏感的数字,为什么必须做成单一真相字段而不是每处现算
- AI 摄像头在门店的低成本落地姿势:不买专用硬件也能跑起来
- 对接外部平台的两条通用教训:把平台的坑写成清单,以及「建单成功不等于业务成功」
- 外围模块的共同套路:复用主干机制,几乎不新造轮子

外围模块的定义很朴素:不是每天都在跑的主干(订货、库存、营业额),但缺了它们,连锁管理就会漏风。这类模块的正确姿势是**小而薄**——每个都尽量骑在已有机制上,而不是自己再造一套账号、一套任务、一套看板。下面逐个过。

## 培训考试:视频 SOP + 在线考试

**解决什么问题**:烧烤门店的核心资产之一是菜品操作的标准化。纸面 SOP 没人看,老带新靠口传心授,新店一开就走样。我们把菜品操作拍成短视频 SOP,配套在线考试:员工看完视频、做完题,系统记录完成度和成绩。

**最值得抄的设计点:培训完成度可以进经营分。** 单独做一个培训系统,最大的死法是"没人学"——通知发了、视频拍了,完成率惨淡。我们的解法不是催,而是把培训完成度接入门店经营分(经营分是什么见[巡检与经营分](inspection.md))。门店店长在乎分数,分数里有培训这一项,学习就有了抓手。**任何"希望门店做但门店没动力做"的事,先想想能不能挂到分上,而不是先想怎么催。**

## 达人探店登记:对运营同学宽进严出

**解决什么问题**:连锁品牌会持续和探店博主合作,需要登记博主信息(平台、账号、粉丝量)和内容效果,否则投放决策全凭感觉。这个模块就是一张结构化的登记台账加简单的效果回看。

**最值得抄的设计点:输入容错,宽进严出。** 填表的是运营同学,不是工程师。粉丝数这一栏,有人填 `30000`,有人填 `3w`,有人填 `3万`。如果前端校验一刀切只收纯数字,结果不是数据变干净,而是运营同学嫌麻烦不填了。我们的做法是**前端宽进**(接受 `3w` 这类人类写法)、**后端归一化严出**(统一解析成数字入库,统计口径永远干净)。脏活让代码干,别让人迁就系统。

## 门店合同与年度运营费:账单自动生成 + 逾期锁订货

**解决什么问题**:加盟门店有合同周期和年度运营费。人工记台账催缴,必然漏——合同散在文件柜里,到期没人知道,欠费门店照常订货。我们的做法:合同到期前自动生成账单,到期未付则锁定该店订货(锁订货是整个系统里最有效的"抓手",详见[订货商城](ordering-mall.md))。

**最值得抄的设计点:折算口径做成单一真相字段 + 每日自愈任务。** 年度运营费涉及折算——门店合同中途签或中途续,费用要按剩余合同月数折算(例如年费 1 万元、剩余 6 个月,则本期应收 5000 元;示例数字,非真实数据)。这个数字如果在账单页算一遍、催缴通知里算一遍、报表里再算一遍,三处公式迟早不一致,财务和加盟商就会拿着两个不同的数字吵架。我们的铁律:**折算结果只存一处**(账单上的单一金额字段就是真相),所有展示读这个字段;再配一个每日定时任务对全量账单重算校验,发现偏差自动修正。口径敏感的数字,宁可"算一次存起来+每天体检",不要"每处现算"。

## 门店投诉:工单化 + 处理时限

**解决什么问题**:顾客投诉如果只是微信群里喊一嗓子,处理与否全看谁看到了。我们把投诉做成工单:登记、指派、处理时限、超期升级,处理过程留痕。

**最值得抄的设计点:和巡检整改复用同一套「任务 + 超期」机制。** 投诉处理和巡检整改在机制上是同一件事——都是"发现问题 → 指派责任人 → 限期处理 → 超期有后果"。我们没有为投诉单独造一套任务引擎,而是直接骑在巡检整改已经跑通的那套任务+超期机制上(见[巡检与经营分](inspection.md))。省下的不只是开发量,更重要的是**门店面对的是同一种交互和同一种后果**,不用学两套规则。

## 门店 AI 摄像头:三条检测线,低成本落地

> 本节是速览;三条检测线的判定思路、误报治理、结果怎么进经营分,完整展开见[业务型 AI:视觉巡检与聊天即操作](../04-ai-engineering/business-ai.md)。

**解决什么问题**:门店服务质量的很多问题,巡检拍照抓不到,只有摄像头看得见。我们在门店已有的普通监控摄像头上跑了三条 AI 检测线:

- **进店问候检测**——顾客进店有没有人招呼
- **营业时间核查**——该开门的时间有没有开门
- **穿戴合规**——员工工装、口罩等是否符合规范

**最值得抄的设计点:抽帧 + 云端识别 + 按店灰度开关,不上昂贵的专用硬件。** AI 视觉在门店落地,最容易被吓退的是成本想象:以为要买带 AI 芯片的专用摄像头、店店装边缘计算盒子。实际上对这三类"分钟级发现就够了"的场景,完全不需要实时流分析——从现有监控**按固定间隔抽帧**,把图片发给**云端视觉模型识别**,结果异常再触发提醒。硬件零新增,成本主要是按帧计费的模型调用。再配一个**按店灰度开关**:先在少数几家店开,验证误报率和成本模型,再逐店铺开。AI 项目死于"一上来全量"的,远多于死于技术不行的。

## 抖音团购:订单核销同步 + 改适用门店先预演

**解决什么问题**:门店在抖音上卖到店团购套餐,总部要知道每家店卖了多少、核销了多少、退了多少。我们对接平台开放接口:每小时增量同步订单与核销,每天凌晨兜底前一天;平台门店按归一化后的名称自动绑定内部门店(宁缺勿错),绑不上的在映射页人工绑;看板给成交、核销、退款与核销率。金额一律按「分」存,口径是用户实付、不含平台补贴(与开票同口径)。评价数据平台没有开放接口,只能在商家后台看——这一点我们核实过几轮,不再找。

**最值得抄的设计点:把平台的坑写成清单,每个坑配一道代码护栏。**

- **限流**:完成平台验收前每天的调用次数有上限(示例:几百次)。定时任务按最省的方式排;手动大区间回填一天只跑一次。
- **分页**:订单查询的游标参数实测不回传,只能按页码翻;门店查询的分页参数名和常见写法不同,传错了不报错、永远回第一页;翻过末页报「参数不合法」而不是回空页——必须按总数停。
- **归属**:核销记录不带门店和订单归属,只能用订单里的券号反查,所以订单必须先同步;订单里的门店名常为空,从门店档案回填。
- **下架判定**:门店档案只返回当前在营的门店,「这一轮没返回 = 已下架」只能在**整轮完整拉到**时判,分页残缺时一律不动。
- **改适用门店**:团购商品的适用门店可以经接口整体改。我们默认**预演**——只出「新增哪些店、去掉哪些店」的清单,管理员确认后才真提交;提交后进平台审核,线上旧版本照卖到过审;平台会自动剔掉它判定停业或不支持的门店,回执里要把被剔的列出来。保存是全量覆盖,有几个必填项读接口永远不回显,每次保存都要补上。

## 物流商仓配:逐单推送,共配和专送绝不并票

**解决什么问题**:门店订货由物流商的仓配一体服务履约——物流商到工厂提货入它的云仓,一仓发往各地门店。出库单在出库动作发生时**逐单推送**(不攒批),批次与效期随单透传;实发、运单与轨迹靠回传。

**最值得抄的设计点(两条)**:

- **共配和专送绝不并票。** 物流商有两条产品线:城配共配(便宜、不保证时间)和冷链专送(能指定送达时间窗,按件加收服务费)。配送方式是**订单级字段**,门店下单时选;推单时按「门店 + 配送方式 + 时间窗」分组合票,同一家店同一天的共配单和专送单绝不合成一票——否则产品类型、计费和时间窗全部错乱。不足最低件数的不支持专送,**直接拒单而不是静默降级**;费率只在价目表里配,前端一个数都不写死。
- **建单成功 ≠ 审核通过。** 同步接口只管「收单」,物流商内部审核失败(月结账户被冻结、地址超出配送范围)时,我们这边一片绿。补了三层:推单后短时快检状态;看门狗每小时扫超时空挂的单;回传状态按码表分流——**只有最终「发货确认」才算实发**,审核失败、下发失败进告警,取消类落「已取消」。超出配送范围的门店配一个「转运地址」。

顺带一句选型:我们也评估过另一家代仓代配方案,接口联调都跑通了,但全口径成本测算比现状贵,最终没切——**对接做完,不等于必须切换**。

## 区域代理:预存货款与自动划店

**解决什么问题**:区域代理是独立主体、独立账套,门店货款进对应主体的账户;工厂若按月结回款,上游采购会缺现金流。

**预存货款**:代理向工厂主体**先款后货**——财务把银行到账登记为充值,总部到代理仓的直通调拨按内部结算价自动冲抵,**每一笔冲抵锚定一张调拨单**,钱链和单据链一一对应;月度结算快照照常轧差。禁止的是没有单据链的拆借式打款。开关分两级:先开记账台账、观察对平;「余额不足整单拦截」是第二级,单独再议。

**按主体拆分核算 + 门店自动划归**:每个代理主体独立账套、独立核算,门店归属哪个主体由系统按地理位置自动划归——以各主体所在地为种子、优先连片,超出距离上限宁可不分,已绑定的门店不动。付款页的收款账户由后端按绑定关系下发,**调整归属不用发小程序版本**。

## 电子签导入:先识别「疑似转让」

**解决什么问题**:门店合同在电子签平台签完后批量导入。同一家店续签时,新合同自动做「续签结转」(收费日沿用);但门店转让给新加盟商时,新合同长得和续签一模一样,被当成结转之后,门店的加盟商和客户档案都没换。

**最值得抄的设计点:预览阶段先识别,提交阶段逼人表态。** 预览时对每一行续签结转比对签约人(手机号优先;旧合同取不到签约人时,看门店加盟商和客户建档时间),对不上就标「疑似转让」、不许自动按续签处理;到期前很久就续签的标灰提示。提交时疑似转让必须二选一:「按转让处理」或「仍按续签」。按转让处理 = 仍走续签结转(收费日**接着前一任往后算**,已有账单不删),额外把门店加盟商换成签署人对应的客户(查不到就拒,不自动建)并记一条转让跟进;免收费资格不随转让继承,但会写提醒。这个口径改过一次:最初设计是「转让 = 解约 + 按签署日重算收费日」,业务确认后作废。转让分支已开启,**首个真实转让还没跑过**,首例要人工逐项核对。

## 礼品商城:一条指引

这一节不算第十个模块,只是指路。积分兑换礼品的商城,属于积分体系的出口侧,机制(积分唯一出口、兑换扣减、礼品管理)已经在[积分体系](points.md)一页讲透,这里不重复。只提醒一句:礼品商城的所有积分变动同样必须走积分唯一出口,不要因为"只是个兑换"就绕开。

## 共同点:复用主干,不新造轮子

回看这一页的九个模块(礼品商城只是指路,不另算一个),会发现它们没有一个是"从零造"的:

| 模块 | 骑在哪个主干机制上 |
|---|---|
| 培训考试 | 经营分(完成度计入分数) |
| 达人探店登记 | 看板/台账体系(结构化数据 + 统计) |
| 合同与年度运营费 | 订货锁(逾期锁订货)+ 定时任务(每日自愈) |
| 门店投诉 | 巡检整改的「任务 + 超期」机制 |
| AI 摄像头 | 提醒/通知链路 + 灰度开关模式 |
| 抖音团购 | 定时同步 + 门店映射表 + 预演确认 |
| 物流商仓配 | 订单级配送方式字段 + 回传状态码分流 + 看门狗 |
| 区域代理预存与划店 | 内账唯一记账出口 + 两级开关 |
| 电子签导入 | 合同续签结转 + 客户档案 |

这正是小团队能维护大系统的原因:**主干机制(积分、任务、锁、看板、定时自愈)一旦打磨扎实,外围需求就变成了"接线"而不是"造轮子"。** 评估一个新需求要不要做时,先问一句"它能骑在哪个现有机制上"——如果答案是"哪个都骑不上,得全新造",要么是主干还缺一块,要么是这个需求本身值得再想想。

## 踩坑与红线

- **症状**:同一笔运营费,账单页、催缴通知、报表三处显示的折算金额不一致,财务对不上账。
  **根因**:折算公式在多处各自现算,某次改口径只改了其中一处。
  **铁律**:口径敏感的金额只算一次、存单一真相字段,所有展示只读该字段;配每日自愈任务重算校验。

- **症状**:登记类模块上线后填报率很低,数据残缺到没法做统计。
  **根因**:表单校验按工程师习惯设计,格式要求过严,运营同学填一次被拒三次就弃用了。
  **铁律**:面向非技术同学的输入一律宽进严出——前端接受人类写法,后端归一化;归一化失败才提示,而不是格式不完美就拒收。

- **症状**:对接物流商后,台账上一批单子全是「建单成功」,门店却迟迟没收到货。
  **根因**:物流商的同步接口只管收单,内部审核失败(账户冻结)只出现在状态回传里,而我们只认了建单响应。
  **铁律**:外部履约一律按「最终状态」而不是「受理状态」记账;状态码按码表全集分流,空挂超时有看门狗。

- **症状**:门店转让后,新加盟商的合同被当成续签导入,门店还挂在上一任名下。
  **根因**:续签和转让在合同字段上长得一样,导入只看门店不看签约人。
  **铁律**:批量导入先预览、先识别,对不确定的行逼人表态;口径改动的分支默认关、首例人工核对。

- **症状**:AI 检测上线初期误报刷屏,门店开始无视所有提醒,连真告警也被淹没。
  **根因**:没有灰度就全量开,误报率没有在小范围验证过。
  **铁律**:AI 检测类功能必须按店灰度,先小范围跑通误报率和成本,再逐步放量;宁可慢,不可狼来了。
