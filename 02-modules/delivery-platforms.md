# 外卖平台集成:插件半自动抓取模式

> 这页讲我们如何在拿不到外卖平台官方 openAPI 的前提下,用 Chrome 插件半自动抓取商家后台数据,把三大外卖平台的营收、竞对、POS 数据接进自己的系统;以及数据接进来之后,违规食安标注和「群里一句话上下架」这两类在它上面长出来的业务。适合被「平台不给 API」卡住的中小连锁 IT 负责人和工程师读。

**读完你会知道:**

- 为什么中小连锁基本拿不到外卖平台官方 openAPI,现实的替代路径是什么
- 插件半自动抓取的原理,平台门店 ID 为什么必须单独建映射表(以及一店多店号怎么办)
- 上报接口为什么必须幂等,采集为什么要有心跳、独立重试窗口和哨兵
- 外卖违规 / 食安怎么从五个来源汇成一张表、按类别分期倒扣经营分
- 门店在群里说一句「缺货下架」,怎么安全地同步到三个平台、联动套餐、到货再恢复

## 一、现实:官方 openAPI 你大概率拿不到

美团、饿了么、京东都有开放平台,但面向的是**服务商**:要企业资质、服务商认证、审核,有的能力只对头部 ISV 开放。中小连锁以自有品牌身份申请商家数据类接口,大概率走不通或权限远不够用。我们的判断很简单:**数据就摆在商家后台页面上,运营同学每天都在看**——问题不是拿不到,而是怎么把人眼看到的数据自动搬进系统。

## 二、方案本体:插件装在运营同学的浏览器里

插件装在运营同学日常办公的 Chrome 里,复用浏览器里现成的登录态,在商家后台页面上把数据读下来,POST 到我们自己的上报接口入库。几个要点:

- **登录态不用管**:不存密码、不对抗验证码、不模拟登录,这是相对无头爬虫最大的优势;
- **只读本商家有权查看的数据**,不越权;
- **插件越薄越好**:只管「怎么抓」,校验、映射、入库全在后端,页面改版只动插件;
- **半自动,不追求无人值守**:原因见「踩坑与红线」。

```mermaid
flowchart LR
    A["运营同学浏览器<br/>已登录平台商家后台"] --> B["Chrome 插件<br/>读取页面数据"]
    B --> C["POST 自家后端<br/>上报接口·幂等"]
    C --> D["平台门店ID映射表<br/>换算成内部门店ID"]
    D --> E["入库<br/>营收/竞对/POS"]
    E --> F["报表·补贴·运营费<br/>等下游业务"]
```

## 三、插件矩阵:一类数据一个插件

| 插件 | 抓什么 | 给谁用 |
|---|---|---|
| 营收账单插件 | 各平台商家后台的月度账单 / 营收明细 | 负责对账的运营同学 |
| 竞对信息插件 | 平台 C 端可见的竞对门店公开信息 | 做市场分析的同学 |
| POS 数据插件 | 收银系统后台的交易数据 | 门店运营口的同学 |

拆开的理由:平台改版只打挂对应那一个插件;每个插件只申请自己需要的域名权限;改版频繁的和稳定的各自迭代。代价是分发麻烦一点,对内部工具可以接受。

## 四、平台门店 ID 映射:单独建表,别塞主表(★重点)

平台门店 ID 与内部门店 ID 是两套体系,而且**平台会换 ID**(重新上单、迁移、换主体),**一店还对多平台**。我们最早偷懒,把美团门店 ID 做成了门店主表上的一个字段,后来单独建了映射表、主表字段标废弃——但**字段还在表里,就永远有人误用**,新同事和 AI 助手看到它顺手就用,数据却早已不准。

后来又遇到反方向的情况:**一家门店在同一平台开了两家店**(比如二店共用一个经营主体)。映射于是扩成「主店号 + 附加店号」:订单归属、推广费、评分按店号分别落,读取按门店求和;按店号计费的规则(如平台运营费)按店号分别判档,不合并后再判。另设一份**忽略名单**,收已解约门店留在账号下的平台店,让它不归属任何门店。注意**忽略 ≠ 解绑**:解绑的附加店号历史归属照旧,只是不再巡检、不再通知;忽略则彻底不算。

铁律:**平台侧 ID 映射从第一天起单独建表,映射表是唯一真相源**,一对多、多对一、忽略都在这张表的语义里表达。

## 五、月度营收抓取 SOP:人机配合,幂等兜底

1. **固定日期执行**:每月固定日期(示例:每月 1 号),运营同学逐平台登录后台,用插件抓上月账单;
2. **逐店上报**:后端按「平台门店 ID → 映射表 → 内部门店 ID」落库;
3. **单店可重抓**:网络抖动、页面没加载全,只重抓那一家,不全量重来;
4. **上报接口幂等**:以「平台 + 内部门店 + 月份」为唯一键 upsert,同键重复上报是覆盖不是累加——平台维度不能省,否则同店同月的两个平台数据会互相覆盖。

人机配合的流程里人一定会重试,幂等是对操作者最基本的善意,也是数据不炸的保险丝。

## 六、挂在抓取数据之上的两类业务

- **引流品补贴**:按商品维度给门店补贴,匹配依据是**建规则时的商品名快照**,并接受「改名后需人工重新对齐」的运维成本;平台侧口径(如按订单量计,示例)一旦定了就写进文档,所有报表、结算、答疑引用同一份。
- **平台运营费**:评分、费率这些平台指标会变,而它们联动我们对门店的收费档位。**规则参数做成可配置**,改配置即生效,不必每次发版,历史规则也可追溯。

## 七、采集健康度:插件也要有心跳(★)

半自动方案最大的风险不是抓错,是**悄悄不抓了**:换了电脑、插件被禁用、登录过期、页面改版,任何一件都会让数据静静断掉。所以我们给所有插件补了统一底座:

- **统一骨架**:常驻脚本 + 页面注入 + 上报模块,只有解析层不同;
- **心跳**:每个插件按自己的频率报活,日频任务的失联阈值略大于一天,否则天天误报;
- **看门狗**:超时没心跳或连续多次零条,告警到工程群;
- **掉登录必须显式失败**:未登录时页面返回空列表是最阴险的失败模式,必须识别并报错;
- **装好即自动跑一次**,周末节假日按业务日历放宽阈值;
- **把「在跑的」和「仓里的」对上**:我们改过一份早已是死代码的插件目录,改了半天毫无效果。

评分与负反馈这类数据又多了三条:

- **快照类数据要有独立重试窗口**。平台评分只给当前值、没有历史接口,当天漏抓永远补不回。评分采集单独排了多次重试(其中一次在独立窗口里跑,不和其他采集共用页面),并在最后一次重试之前设一个告警时点,让人还有机会当天手动补。
- **负反馈带着平台自己的统计窗口**。食安 / 服务负反馈是滚动窗口(示例:近 30 天、滞后几天放出),单位是「每万单」而非百分比。我们按比平台更宽的范围扫明细、自己按订单日期计数,并加**哨兵**:多家店有率而明细全为零,判采集失败而不是「没事」。
- **同一浏览器里的采集会互相污染**。排查时打开过某个单店页面,页面把「当前门店」写进了会话,另一个本该看全部门店的采集从此静默变成单店模式。采集专用浏览器不拿来手动排查,或排查完复原会话状态。

## 八、同一个指标,三个平台可能编码完全错位(★)

差评申诉的状态字段三个平台都有,但编码**互相错位**:同一个数字在 A 平台是「申诉成功」,在 B 平台是「申诉失败」。照抄的后果是把失败的申诉当成功从考核里剔掉——门店差评率被做好看,而这是要考核和罚款的数据。铁律:**跨平台同名字段,每个平台单独取真实样本验证语义**,映射表连同验证依据写进文档。顺带:有官方 API 的渠道(如短视频平台的到店团购)优先走 API;平台评价类接口常不给当天数据,日报要么延后一天,要么明示口径。

## 九、违规与食安:五源标注,按类别分期倒扣经营分

外卖食安线索散在五处:平台食安负反馈、服务负反馈、平台违规罚单、顾客在 IM 里的食安投诉、差评里归因为食安的。我们把它们汇进**一张事件表**,运营逐条标注,标注属实才倒扣门店经营分(见[巡检与经营分](inspection.md))。

- **入表即去重合并**:同一来源同一事件只入一次;同平台同订单号从多个来源进来的并成一件主件,其余挂作证据。资质到期类平台通知只提示,不进待标注队列。
- **规则给建议,人定性**:按关键词给建议分类和建议严重度;食安属实必须由运营定严重度等级(示例:1~5 级),规则没命中却按默认级别判食安的必须写备注;批量标注不接受「属实 + 食安」,食安只能逐条判。
- **按类别分期生效**:每类各有生效日,按**事件发生日期**比较;生效日前的事件只算「预计扣分」,门店群通知标为预览。示例做法:先开食安类,一个月后再开服务负反馈与平台罚单类。生效日可按类提前或推迟,但有最早日期钳住,历史月份永不追扣。
- **改判可重算**:已被经营分算进去的事件改判,同步重算该店当月分数,分数变了才发更正。
- **通知与积压**:每天固定时刻按门店合并成一条发门店群(顾客原话脱敏,门店有异议期);每天早上把待标注积压数发运营群——**不标注就永远不会扣**,积压本身就是要盯的指标。

差评率已经在经营分里算过一次,所以差评只作证据,改判为食安才扣,同一件事不扣两次。

## 十、聊天即操作:群里一句话,三平台同步上下架

门店缺货要下架一道菜,原来得分别登三个后台,含这道菜的套餐还要一个个找。现在门店在自己的门店群里 @机器人 说一句「鸡翅缺货下架」:

1. **只读预览**:按各平台**本店真实菜单**模糊匹配(同一道菜各平台叫法不同也认),列出现状和会被联动的套餐;匹配不唯一就列候选请门店挑,多出实质字的(「泡椒鸡翅」对「鸡翅」)只当候选不自动认。
2. **两段式确认**:门店回「确认」才建操作单,机器人这一步只说「已提交,结果稍后回报」;每次确认**有且只有一条**群回报(成功、失败、过期都报),没办成的同时转运营。
3. **套餐联动**:下架时含这道菜的在售套餐一起下(门店可说「套餐不动」);上架时**只恢复系统因这道菜下架的套餐**,且它的其他起因菜也都已在售才恢复;商家后台手工下架的套餐永不自动恢复。每次改动都记进上下架台账。
4. **到货提醒恢复**:背后有订货商品的菜,相关订货单签收到店后提醒「是否恢复上架」;本地采购的菜次日提醒。**恢复同样要门店回确认**。

授权口径:绑定了门店的群里任何人都能操作,门店身份由群绑定注入,不信文字里写的店名。每个平台的写入独立开关,未经真实会话验证的保持关闭,关闭时预览照常、确认后转运营。操作单领取后限时无回执即判过期,**过期的单绝不重发**——上下架重复执行比没执行更难收拾。

## 踩坑与红线

- **平台页面改版,抓取一夜全挂**
  症状:某平台数据全部缺失。根因:插件解析的是别人家的页面结构,改版就是破坏性变更,天生脆弱。
  铁律:失败当天就告警 + 手工导出 / 录入通道永远保留;把插件当「随时会坏的东西」运维。
- **追求全自动,越做越脆**
  症状:登录过期、验证码、风控弹窗轮番出现。根因:全自动要对抗平台的反自动化机制。
  铁律:接受半自动定位——**数据对才是需求**,人点一下的成本远低于对抗风控。
- **平台 ID 塞进门店主表,废弃后阴魂不散**
  症状:停维护的字段仍被新代码(含 AI 生成的)引用。根因:字段物理存在就是误用邀请。
  铁律:映射单独建表;已铸成的废弃字段在项目文档最显眼处反复标注。
- **上报接口累加式入库,重试变灾难**
  症状:某店某月营收莫名翻倍。根因:没按「平台 + 店 + 月」唯一键覆盖。
  铁律:一切人工可触发的上报接口必须幂等。
- **采集断了、或「成功」返回全零,没人知道**
  症状:数据静静停了几天,或明细全零而率不为零。根因:失败模式是「成功返回零条」。
  铁律:**心跳 + 零结果告警 + 率与明细互校的哨兵**;快照类数据设当天告警时点。
- **跨平台同名字段直接照抄语义**
  症状:某平台申诉成功率异常高。根因:状态编码互相错位而字段名相同。
  铁律:每个平台的枚举值逐一取真实样本验证。
- **一道菜被重复上下架**
  症状:平台上的状态与门店意图对不上。根因:超时的操作单被重发。
  铁律:**写平台的操作单过期即终态,绝不重发**;每次确认只回报一次。
