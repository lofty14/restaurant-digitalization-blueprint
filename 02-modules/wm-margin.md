# 外卖逐单毛利:成本卡 × 订单明细 × 红线诊断

> 这页讲我们怎么把外卖从「只知道卖了多少」做到「每一单赚了多少」:菜品成本卡 + 平台订单明细 + 一套口径校准,最后收敛成一条可播报的毛利红线。适合外卖占比高、却说不清哪家店在赔钱的老板和运营负责人读,工程师读第三节以后。

**读完你会知道:**

- 为什么「营业额 − 食材采购额」算不出外卖毛利,必须逐单算
- 毛利公式怎么拆:实收、食材、包装、辅料、推广费各自的口径与陷阱
- 成本卡的三个建模决策:按订单日取版本、按最小单位建卡、套餐自动拆解
- 覆盖率工程——把「算不出成本的订单行」从一半降到接近零的四种招式
- 逐单数据天生不准时怎么办:用权威日表做「校准口径」
- 红线诊断怎么从一张表变成每周自动播报,以及播报冤枉门店的三个致命陷阱

## 为什么必须逐单算

外卖是很多餐饮连锁利润波动最大的一块:平台佣金、配送费、活动补贴、推广投放各走各的账,月底看到的只有一个「结算实收」。老板真正想知道的是「哪家店、哪个品、在哪个平台上赚不赚钱」——这三个维度,任何汇总口径都答不了。

「月营业额 − 月食材采购额」这类粗算不成立,原因很实在:采购是批次的、有库存滞后,外卖只是门店总出货的一部分,活动品和赠品的成本结构又完全不同。要回答上面三个问题,只有一条路:**把每一单的每一行菜,乘上它那天的成本卡**。

于是模块被拆成两半:

- **左半边:订单明细从哪来** —— 平台大多不给逐单明细 API,我们走的是插件半自动抓取(见[外卖平台集成](delivery-platforms.md)),把三个平台的订单行统一成一张明细表;
- **右半边:成本从哪来** —— 菜品字典 + 成本卡,成本卡的原料成本又接回[生产与成本](production-costing.md)的自产成本口径。

两半在「订单行 → 菜品 → 成本卡」这条匹配链上会合。整个模块九成的工程量,都花在这条链的**匹配率**上。

## 毛利公式:五项,每项都有坑

我们最终固化下来的公式(具体系数按自己业务测,以下均为结构):

```
单店单期毛利 = 权威实收
             − 逐单食材成本(订单行 × 当日成本卡)
             − 包装成本(每单固定值)
             − 辅料成本(实收 × 比例系数)
             − 推广费(仅门店自付的那部分)
```

逐项说明它为什么长这样:

1. **实收**:必须是「扣完佣金和配送费」的净收入,不是顾客付款额。这个数在平台结算日表里最权威。
2. **食材**:唯一逐单计算的项,也是唯一需要成本卡的项。
3. **包装**:每单一个固定值(打包盒/袋/封条),不随菜品变——试过按菜品摊,收益极小、维护成本极高,放弃。
4. **辅料**:油、调料、一次性手套这类「摊不到具体菜」的消耗,按实收的一个比例系数扣。系数是拿一段时期的实际领用量除以同期实收测出来的,写在配置表里可调。**注意防双计**:走了比例系数,成本卡里的辅料项就必须留空,否则同一笔油钱扣两遍。
5. **推广费**:平台推广花的钱不在订单里,得单独导入。**只算门店自付的那部分**——总部品牌账号统一投放的钱属于总部营销费用,摊到门店头上会让所有店集体「不达标」。

> 公式里的每一个系数都应该是配置项,而不是写死在代码里。我们吃过写死的亏:老板拍板改口径那天,要动三个文件、跑一次全量重算。

## 成本卡的三个建模决策

**决策一:成本卡按订单日取版本。** 成本卡带生效日期,算某一单的成本时取「生效日 ≤ 订单日」里最新的那一版。这样改卡不会改动历史毛利——不然运营今天调了个价,上个月的月报明天就变了,报表立刻失去公信力。要修正历史,把生效日填成过去某天并显式触发重算,是一个有留痕的动作。

**决策二:按最小单位建卡,份量交给拆解器。** 同一个菜在平台上常有「10 串装 / 15 串装 / 单支」多个 SKU。逐个建卡会有 N 倍的维护量,而且改一次料要改 N 张。正确姿势是:**卡建在最小单位上(比如一支),平台上的多份量 SKU 由解析器按份量自动折算**。

**决策三:套餐必须显式拆解。** 套餐行只有一个价,成本得拆到子菜。我们做了两条路:能从平台商品结构解析的自动拆,解析不出的进「待定义队列」,让运营在页面上点几下把组成填上。**没拆的套餐绝不能猜一个成本了事**——宁可标成「未覆盖」,也不要往报表里灌假数。

这里有一个隐蔽但代价极大的坑:某张卡的「来源类型」误填成了「套餐组合」,而这个菜其实没有子菜。结果是——卡明明建好了,成本却永远算不出来,而且看板上它长得和「没建卡」一模一样。**所以查未覆盖必须分两类**:A 类=订单行没匹配上菜品,B 类=匹配上了但成本卡算不出数。只盯 A 类,会朝着错误的方向查上一整天(我们查了,B 类的数量是 A 类的十倍)。

## 覆盖率工程:让匹配链自己长大

「订单行 → 菜品」这条匹配链,靠人工维护是维护不动的:门店随时改菜名、加后缀、上新品。我们用四种招式让它自己长:

| 招式 | 做什么 | 效果 |
|---|---|---|
| **平台码绑定表** | (平台, 平台商品码) → 菜品 ID,是最可靠的一级匹配 | 绑一次永久生效 |
| **别名自学** | 定时任务扫未匹配行,把新出现的名字归一化后挂到已知菜品的别名字典 | 改名自动跟上 |
| **自动绑定** | 别名命中后,反过来把「平台码 → 菜品」写进绑定表 | 下次走一级匹配,更快 |
| **精确名兜底** | 平台码为空的行,用归一化后的名字直接等值命中别名字典 | 捞回一批漏网 |

配套一条纪律:**名字归一化规则改动前,必须做新旧规则的影子比对**。我们加过一个前缀剥离词,结果把某个品的历史名切成了两个不同的键,同一个菜在报表里裂成两行。改归一化 = 改所有历史数据的分组键,必须先拿全量别名跑一遍新旧对照。

## 校准口径:承认逐单数据不完美

逐单数据有一个天然缺陷:**订单快照不会回冲后续发生的退款**。顾客第二天退了款,那一单的实收在我们库里还是原值。有些平台开放了订单重拉接口(可以定时把前几天的单重新拉一遍、把退款冲掉),有些没有。

所以月报不能直接用逐单实收求和,而是走**校准口径**:

- 以 (平台, 门店, 日期) 为最小单元;
- **实收**用平台结算日表的权威值替换;
- **成本**按「该单元里算得出成本的订单占比」折算,即 `成本 × 单量保留率`;
- 报表上同时给出「数据完整度」——这一格有多少订单是算得出成本的。

关键是**把不确定性明示出来**,而不是抹平。我们在看板上把「覆盖率 / 未覆盖金额」合成一列「数据完整度」,悬停看明细;月报上写的是「覆盖单毛利率」,而不是假装全量。业务同学一旦发现你在报表里藏过一次不确定,以后所有数字都要被追问。

## 特殊口径:三条老板拍板的规则

这类规则每家都不同,但**都得显式写下来、显式配置化**,否则半年后没人说得清报表为什么这么算:

- **公司补贴的引流品,食材成本记零。** 引流品的补贴是另行结算的,再往菜成本里记一遍就是双计。配置形如 (平台, 商品名) → 成本置零,运营改配置立刻生效。
- **门店自设的赠品,成本按一份封顶。** 「点红心送 X」这类活动,顾客可能一单点 N 份,实际只送一份。识别靠订单行的关键词特征 + 极低均价。注意区分「X 元购」这种真促销购买——那是要算成本的。
- **数量量纲归一。** 部分门店把「一份 N 支」的品按支数传数量,不处理的话单行成本会翻十几倍,一条脏行就能造出一大笔幻影成本。规则:菜名里带明确支数(N ≥ 阈值)的卡按份计价,行数量能被 N 整除时折成份数。

> **量纲是这个模块的头号杀手。** 采购价、成本卡、订单行三处的单位只要有一处对不上,算出来的毛利就是纯噪声,还长得很像真的。

## 红线诊断:从一张表到每周自动播报

有了逐单毛利,下一步是让它推动经营动作。我们的做法是设一条**毛利红线**(示例:扣完食材、包装辅料、推广费后毛利率低于 35% 即不达标,阈值按自己业务定),然后:

1. **按店诊断 + 归因**:把每家不达标店的三个因子(食材成本率、推广费率、客单价)分别与全网中位数比,找出最异常的一到两个,给出主因和改进方向;
2. **数据不足不判**:单量太少或覆盖率太低的店,单独列「数据待补」,绝不硬判——把数据缺口播成「经营差」是最伤信任的事;
3. **播报双频**:每月一次全量月报;每周一次周报,**只播「本周新跌破」和「继续下滑」的店**,没有新情况就不发。

第三条是运营体感的关键。周报如果每周把同一批店重播一遍,两周后就没人看了;**只播变化**,群里每条消息都有信息量。

播报之前还有一道人工闸:第一次跑出的不达标名单,先抽查两三家验证。我们第一次跑出来一批「食材成本率异常高」的店,抽查后发现多数是成本卡不适配,而不是门店真的在乱用料——直接播出去就是冤枉人。**自动播报的前提是先人工验一轮**。

## 踩坑与红线

**坑一:推广费率把「数据缺口」算成了「投流过猛」**

- 症状:某店诊断结论是「推广费率畸高」,运营去查,门店根本没多投。
- 根因:推广费是整月的,而该平台的逐单数据只从月中某天开始有——分母只有几天实收,分子是整月费用,费率直接虚高一倍。
- 铁律:**推广费率的分子分母必须落在同一个时间窗**。按「该平台实际有数据的天数」折算,分子分母一起折,少折一边错得更离谱。

**坑二:真实值与估算值混在同一个窗口里比较**

- 症状:周报冒出一批「新跌破」的店,复查全是假的。
- 根因:上周窗口里有真实推广费数据、本周还没导入走的是估算值,两个口径直接相减。
- 铁律:估算与否要**按月判断**(该月是否已导入),并把「窗口内估算天数占比」记下来;跨口径的同比环比一律标注或不出。

**坑三:基准取错,所有投流的店都被判有罪**

- 症状:凡是投了推广的店都被诊断为「推广费率高于中位」。
- 根因:中位数是在「所有店」上算的,而半数店根本没投流、费率为 0,把中位压到了接近零。
- 铁律:**做基准比较前先问「这个基准的样本该不该包含零值」**。费率类基准只取真正发生了该项支出的样本。

**坑四:自动化不闭环,人肉补数补到死**

- 症状:每天有人手动跑重算、手动绑菜名。
- 根因:匹配、绑定、重算是分散的手工动作。
- 铁律:做成一条**每小时的自动流水线**:补采集 → 学别名 → 拆套餐 → 自动绑定 → 应用护栏内的智能建议 → 重算近两天。所有自动动作留操作日志、可整批撤销;需要人的只剩「新品定义组成」和「每月导一次推广费」。

**红线汇总**

- 成本系数(包装/辅料比例/红线阈值)一律配置化,不写死在代码;
- 成本卡按订单日取版本,改卡绝不改历史;
- 未覆盖必须分「没匹配上」和「匹配了算不出」两类查;
- 报表明示数据完整度,绝不用全量口径包装覆盖不全的数;
- 自动播报前先人工抽查一轮,数据不足的店只列不判。
