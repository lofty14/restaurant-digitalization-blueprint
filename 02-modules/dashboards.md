# 看板与车间大屏:数据怎么被真正看见

> 这页讲我们把数据送到三种屏幕上的经验:管理端看板、门店手机上的卡片、以及挂在工厂墙上的大屏/电视墙。适合已经把数据算对了、却发现「没人看」的老板和 IT 负责人读。

**读完你会知道:**

- 看板、卡片、大屏是三种不同的东西,混做一定失败
- 挂墙屏幕的登录问题怎么解:免登令牌 + 页面白名单,以及白名单里绝不能放什么
- 大屏上该放什么指标、不该放什么(我们砍掉了行业里最流行的两个)
- ★均值骗人、中位数照妖:一个把看板做错的经典方式
- 一次量纲事故:大屏上的产量数字曾经小了几百倍,没人发现

## 三种载体,三套设计

| | 管理端看板(PC) | 门店卡片(手机) | 车间/门店大屏 |
|---|---|---|---|
| 谁看 | 总部同学,主动查 | 店长,顺手看 | 路过的所有人 |
| 停留时长 | 分钟级 | 秒级 | 一瞥 |
| 交互 | 筛选、下钻、导出 | 点开二级页 | **零交互** |
| 设计重点 | 口径清楚、能导出 | 一屏说完、别让人滑 | 三米外看得清 |

最常见的错误是**把 PC 看板直接投到墙上**:字小、图密、需要交互,挂上去就是一张没人看的壁纸。大屏必须重新设计,而且要**为「一瞥」而设计**——一屏最多三到五个数,配色靠对比不靠信息密度。

## 挂墙屏幕的登录问题

大屏挂在车间和门店,不可能让它一直保持某个人的登录态——设备可能被任何人碰到,登录态泄露等于整个后台泄露。

我们的解法是**免登令牌 + 页面白名单**:

- 给每块屏发一个长期令牌(带签名和有效期),URL 里带上它就能打开;
- 令牌**只能访问白名单里的几个大屏页面**,任何其他页面一律拒绝;
- 白名单里**绝不能放全量总览页**——总览页往往能下钻到经营数据、成本、门店排名,这些不该出现在一块随时被人拍照的屏幕上;
- 屏幕上展示的板块单独挑,机密板块(成本、毛利、财务)不上墙。

这条要固化成规矩:**「挂墙可见 = 对外可见」**。任何往大屏白名单里加页面的动作,都按对外发布来审。

## 大屏上放什么:我们砍掉的两个指标

做车间大屏时,行业里最常被提起的两个指标是**节拍**和 **OEE**(设备综合效率)。我们评估后都砍了,理由:

- 它们要求「设备开停机时间、故障时长、标准节拍」这些数据是准的,而在人工工序为主的食品加工车间,这些数据要么采不到,要么采到的是假的;
- 建立在假数据上的指标,会引导出错误的管理动作。

留下的是**工人能看懂、能马上影响**的东西:今天该做多少、已经做了多少、当前批次是什么、有没有异常告警。**大屏是给一线看的,不是给参观的人看的**——如果一块屏只有老板带客户参观时才有用,它就该被砍掉。

## ★均值骗人,中位数照妖

一个反复出现的看板设计错误:所有汇总都用平均值。

- 门店日均营业额:少数几家高营业额门店会把均值拉到「大多数店都达不到」的位置;
- 工序平均耗时:一次异常停机就能把整条产线的平均值拉长一倍;
- 平均毛利率:被几个极端值主导,看不出真实分布。

**默认给中位数,必要时均值和中位数并排给,再加一个分布图。** 这一条改完之后,好几个「看起来没问题」的板块立刻暴露出了真实的分化。

## 一次量纲事故:产量小了几百倍

我们的生产大屏上线后,产量数字长期偏小,没人发现——因为没人知道它「应该是多少」。后来核对时才发现:**报工按「份/包」记录,而大屏按「吨」显示,中间的换算取了错误的规格**,数量级差了几百倍。

教训有三条:

1. **凡是跨单位显示的数字,必须有量纲哨兵**:在计算链上加一个合理性校验(比如日产量超出历史区间 N 倍或不足 1/N 就告警),让机器替人质疑;
2. **大屏数字要能一键下钻到原始记录**——哪怕大屏本身零交互,后台也要有对应的明细页,方便有人质疑时立刻验证;
3. **新上线的看板,第一周必须人工对拍一次**,拿一天的真实业务数据手算一遍。上线即信任是最贵的习惯。

## 电视墙:视频 + 网页轮播

工厂的电视墙同时承担两件事:监控画面和数据页面。几条实操经验:

- **视频流优先走本地**,不要全部走厂商云——云端按并发路数计费,几十路主码流的月成本高到离谱,而且并发超限时画面直接全黑。本地录像机 + 播放盒子 HDMI 直连,成本是一次性的;
- **子码流足够**。墙上一格画面只有几百像素宽,推主码流纯属浪费带宽和存储;
- **要有夜间守护**:大屏页面挂久了会白屏、会被系统休眠,配一个定时脚本负责熄屏/唤醒/刷新;
- **切换画面做成一句话**:在 IM 里说「切到外卖」,后台推指令给盒子换页面。让墙上的内容可以被随口改变,它才会被真的用起来。

## 踩坑与红线

**坑一:大屏页面在老设备上白屏**

- 症状:同一个页面在电脑上正常,挂在墙上的电视/盒子里一片白。
- 根因:老 WebView 内核不支持较新的 CSS 语法或 JS 语法目标,直接解析失败。
- 铁律:**大屏页面单独设更保守的编译目标和 CSS 兼容底线**,并且必须在**真机**上验收——模拟器和你的电脑都不算数。

**坑二:图表重绘之后点击失效**

- 症状:切换筛选条件后,图表还在,但点击没反应。
- 根因:重绘时销毁重建了实例,事件绑定丢了。
- 铁律:封装的图表 hook 里,**重建实例后必须重新绑定事件**;所有「重绘」路径统一走一个函数。

**坑三:CDN 缓存让大屏停在旧版本**

- 症状:发布了新版本,墙上的屏还是旧的。
- 根因:边缘缓存把前端入口文件缓存住了,而大屏永不刷新。
- 铁律:发布流程里包含**边缘缓存刷新**,并且大屏页要有定时自刷新。

**红线汇总**

- 挂墙 = 对外,白名单按对外发布标准审,机密板块不上墙;
- 大屏零交互、为「一瞥」设计,不放采不准的指标;
- 汇总默认中位数,均值要标注;
- 跨单位数字必须有量纲哨兵 + 上线首周人工对拍;
- 大屏页面必须在真机上验收。
