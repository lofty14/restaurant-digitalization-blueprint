# 业务模块全景与阅读顺序

> 这一层把我们整套系统拆成 26 个业务模块逐一讲透。本页是地图:先看全景表知道每个模块解决什么问题,再按推荐顺序进正文——老板可以只看每页开头的导读,工程师建议顺着主线读完。

## 读完你会知道

- 这一层 26 个模块页各自解决什么问题、现在是什么状态,哪几页是主线、哪几页可以按需跳读
- 为什么推荐从核心域读起,而不是从最"值钱"的财务或生产读起
- 每一页的统一结构长什么样,怎么用它快速跳读
- 贯穿所有模块的四个设计套路:**状态机、快照、唯一出口、口径文档**

## 推荐阅读顺序

```
core-domain → ordering-mall → inventory → points → 其余按兴趣
```

为什么是这个顺序:

- **[core-domain](core-domain.md) 是地基。** 门店、员工、角色权限被后面每一个模块引用,不先搞清"谁在哪家店、有什么权限",读任何模块都会卡壳。
- **[ordering-mall](ordering-mall.md) + [inventory](inventory.md) 是交易主线。** 订货产生单据,单据驱动库存变化,这条链是整套系统里数据量最大、口径要求最严的部分,后面生产、供应链、财务全都挂在这条线上。
- **[points](points.md) 是"唯一出口"的最小样板。** 积分模块业务简单,但把"所有变更走同一个函数"这个模式做得最纯粹——先在这里看懂它,再去读库存和财务里更复杂的版本,会轻松很多。
- **其余按兴趣。** 做运营管理的看 turnover / daily-ops / inspection;做增长的看 site-selection / crm / delivery-platforms / wm-margin / wm-ai-service;做供应链和工厂的看 production-costing / quality-control / iot-coldchain / equipment-automation / factory-ai-inspection / certification-records / supply-chain / smart-supply;做财务与内控的看 finance-ledger / invoice-tax / expense-payroll / asset-management;做数据呈现的看 dashboards。彼此依赖不强,可以跳读。

三条后来才补上的支线,值得单独点名——它们都是「主线跑通之后,真正开始赚钱/省钱」的部分:

- **[外卖逐单毛利](wm-margin.md)** 挂在[外卖平台集成](delivery-platforms.md)和[生产与成本](production-costing.md)之间:前者给订单明细,后者给成本口径,它负责把两边乘起来;
- **[费用审批与工资](expense-payroll.md)** 是[内账引擎](finance-ledger.md)的上游单据来源,把「审批完还要人工誊账」这段砍掉;
- **[冷链温控与工厂 IoT](iot-coldchain.md)** 是[生产](production-costing.md)的感知层,温度数据最终要落到批次追溯里。

### 2026-10 新支线:AI 接管一线

主线和三条支线跑通之后,系统开始从「给人看的数」走向「替人干的活」:AI 在外卖平台上回顾客、按品自己下采购单、盯工厂摄像头、在收工后关冷机。新增的 7 页各自挂在一个上游之后:

- **[线上客服 AI](wm-ai-service.md)** 挂在[外卖平台集成](delivery-platforms.md)之后:采集与平台门店映射是它的眼睛和手,它负责把顾客消息变成代回、转人工或一通电话;
- **[智能采购与排产](smart-supply.md)** 挂在[供应链协同](supply-chain.md)与[库存](inventory.md)之间:库存给现量与在途,补货四层给「该补多少」,它把建议变成每天的草稿,再逐品放权;
- **[开票、税务与资金侧自动化](invoice-tax.md)** 挂在[内账引擎](finance-ledger.md)之后:凭证引擎跑顺了,付款、开票、申报、关账才有地方自动落账;
- **[工厂摄像头 AI 巡检](factory-ai-inspection.md)**、**[机组联网与收工自动关机](equipment-automation.md)**、**[质检与计量](quality-control.md)**、**[认证记录自动生成](certification-records.md)** 四页围绕[生产](production-costing.md)与[冷链](iot-coldchain.md):巡检看人、质检看产品、机组自动化管设备,认证记录再把它们连同生产与冷链的数据排成审核员要的表。

这条支线共守一条纪律:**先影子、再试点、最后放权;AI 只标记不改分,只出草案不改档案。** 全景表「状态」列里的影子运行、试点中,就是这条纪律在现场的样子。

## 每一页长什么样(可跳读)

这一层所有页面结构统一,方便按需取用:

- **导读**(引用块)——这页讲什么、谁该读,10 秒钟决定读不读

只想抄作业的读者,可以每页只看「踩坑与红线」和「延伸阅读」里的 prompt 链接。

## 一个贯穿全层的观察:四个词会反复出现

读的时候留意,几乎每个模块都在重复同一套设计:

1. **状态机**——单据、工单、线索、整改任务,凡是"有生命周期的东西"都用显式状态字段管理流转,禁止用时间戳或布尔值隐式推断状态。
2. **快照**——单据生成时把价格、名称等易变字段冻结成 `snap_*` 快照字段,历史数据绝不读实时值。订货商城是最典型的一页。
3. **唯一出口**——积分、库存这类"账本型"数据,所有增减收敛到一个函数入口,谁绕过谁背锅。这是我们防数据烂账的头号手段。
4. **口径文档**——每个模块配一份说清"数字怎么算"的文档,业务问口径先看文档再看代码。口径没写下来,等于没有口径(为什么这么说,见 [数据口径:最贵的一类坑](../03-pitfalls/data-caliber.md))。

这四个套路不是事先规划出来的,是被坑教出来的——正文里每次出现,基本都能找到一次对应的事故。

## 关于生产与财务两页的特别说明

[production-costing](production-costing.md) 和 [finance-ledger](finance-ledger.md) 涉及我们的商业机密。这两页**只讲结构与模式**:模型怎么拆、状态怎么流转、事件怎么驱动凭证——不含任何真实配方、原料用量、工艺参数,也不含任何真实财务数据。你能学到的是"怎么建这套系统",而不是"我们的配方和账本长什么样"。2026-10 新增的[质检与计量](quality-control.md)与[开票、税务与资金侧自动化](invoice-tax.md)分别是这两页的延伸,同守此约定。
